# AGENTS.md -- Repository rules for Codex agents/contributors

## 1) Session Startup + Access
- At the start of every Codex session, explicitly state: `AGENTS.md has been processed`.
- Agent has full read/write repo access, constrained by this file.

## 2) Mission and Scope
- Build a Warhammer 40,000 (10th Edition) two-army game engine using the latest:
  - core rules/game flow, datasheets, balance dataslates, FAQs, errata, MFM points, faction packs.
- Do not implement content tied to: Crusade, Forge Worlds, Legends, Boarding Actions, Kill Teams.
- If a request depends on out-of-scope content, stop and ask the developer.

## 3) Sources of Truth and Docs
- Docs live in `docs/`; behavior changes must update docs (or add missing docs).
- If adding a decision kind to `src/warhammer40k_ai/engine/decision_kinds.py`, update `docs/DECISION_TYPES.md`.
- First-choice structured data source is JSON under `wahapedia_data/` for:
  - ability, faction, detachment, wargear, stratagem, enhancement, model, wargear options, keyword, datasheet.
- Rules interpretation priority:
  - official Warhammer Community sources/PDFs first, always latest versions only.
  - do not implement outdated rules text.
- `wahapedia.ru` is last resort only when official + in-repo sources are insufficient.
  - If used, tell the developer: official sources checked, ambiguity remaining, and proposed interpretation text.
  - If sources disagree, ask the developer before implementation.

### Generated support matrix docs (mandatory)
- Detachment support is generated by `scripts/generate_ability_support_matrix.py`.
- When changing detachment-ability support:
  - update `_detachment_ability_support_by_name()`.
  - if fully supported, add matching patterns in `_detachment_full_consumption_patterns()` to avoid auto-downgrade to Partial.
  - regenerate docs with `python3 scripts/generate_ability_support_matrix.py`.
  - confirm corresponding `docs/factions/` output matches expected status.
- Datasheet/ability support status in markdown is also generated by `scripts/generate_ability_support_matrix.py`.
- When implementing ability support in engine logic:
  - update the support classifier logic in `scripts/generate_ability_support_matrix.py` so the ability is classified as supported.
  - regenerate docs with `python3 scripts/generate_ability_support_matrix.py`.
  - confirm `docs/ABILITY_SUPPORT_MATRIX.md` and corresponding `docs/factions/*.md` entries show the updated supported status and engine note.

## 4) What "Implement Support" Means
Unless explicitly waived by developer, all are required:
1. Engine hooks: domain model + resolution logic, correct phase/timing integration, deterministic/reproducible behavior.
2. UI hooks: UI-facing state/events/prompts; human choices represented as explicit engine decisions.
3. Tests: new/updated tests for behavior, edge cases, regressions; runnable locally + CI.
4. Docs: update `docs/` for behavior, assumptions, limitations.
5. Support-matrix parity: update support-matrix classifier rules and regenerate markdown support docs so newly implemented abilities are marked supported.

## 5) Choices, Dialogs, and Local/Remote Parity
- If rule text implies optional choice ("you can/may/player can"), surface it as a UI dialog and explicit decision/action.
- Preferred optional pattern: one selection dialog with eligible options plus `None` option.
  - Do not use separate Yes/No then selection dialogs.
- Any choice/prompt feature must support both local and remote play.
- Every decision must use deterministic decision/action interfaces used by remote mode.
- Do not ship local-only choice behavior; if remote parity is blocked/unclear, stop and ask developer.

## 6) Testing Policy (pytest)
- Tests are in `tests/`; framework is `pytest` with xdist settings in `pyproject.toml` (`-n auto --dist loadscope`).
- Markers:
  - expensive deterministic tests: `@pytest.mark.slow`
  - multi-subsystem/E2E tests: `@pytest.mark.integration`
- Commands:
  - full coverage/default: `uv run python -m pytest tests/`
  - fast iteration: `uv run python -m pytest tests/ -m "not slow and not integration"`
- Minimum for every change:
  - run and pass all newly added tests.
  - run relevant impacted existing tests.
- For large feature or rule-behavior changes: also run full suite (`uv run python -m pytest tests/`).
- Ensure command timeouts in local/CI environments are long enough for suite completion.
- Report with submissions:
  - exact pytest command(s), pass/fail, and skipped tests (skips require developer approval).

## 7) Engineering Constraints
- Avoid `try/except` unless strictly needed; never use broad catches (`except Exception`, bare `except`).
- If catching exceptions, use specific types and preserve context/stack; re-raise or raise clear actionable errors.
- No backwards-compatibility shims or fallback code.
- Favor correctness/clarity/composability over speed of delivery.
- Avoid duplicated logic; extract shared code and add focused tests.
- Keep files/modules cohesive and small; maintain clear boundaries (engine vs UI vs parsing vs tests).
- Keep dependency direction such that the engine remains independent of UI.

### Unit module specialization (mandatory)
- Keep `src/warhammer40k_ai/units/unit.py` as facade for `Unit`, `UnitRoundState`, `MovementAction`, `MovementState`.
- Add new `Unit` behavior in `src/warhammer40k_ai/units/unit_mixins/` (not back into `unit.py`).
- Preserve stable imports/patch points:
  - `from warhammer40k_ai.units.unit import Unit`
  - `warhammer40k_ai.units.unit.get_roll` (tests patch this symbol directly)
- If moving methods with local relative imports, adjust import depth for `unit_mixins` location.
- Keep shared mixin helpers in `src/warhammer40k_ai/units/unit_mixins/_common.py` (or utilities), avoid cross-mixin duplication.

### Stratagem module specialization (mandatory)
- Keep `src/warhammer40k_ai/rules/stratagems.py` as facade/orchestrator for `StratagemManager`.
- Add faction/detachment-specific candidate/target helpers in specialized `src/warhammer40k_ai/rules/stratagems_*.py` modules
  (e.g. world_eaters, chaos_knights, chaos_daemons, necrons, aeldari, orks), not by re-expanding `stratagems.py`.
- Preserve stable import: `from warhammer40k_ai.rules.stratagems import StratagemManager`.
- Centralize shared eligibility helpers (e.g. battle-shock/embarked checks).
- Candidate output from specialized helpers must be deterministic and sorted by canonical entity id.

### AI foundation module specialization (mandatory)
- Keep AI reintroduction components modular; do not fold back into `game.py`.
- Maintain dedicated modules:
  - `src/warhammer40k_ai/engine/decision_record.py`
  - `src/warhammer40k_ai/engine/state_blob.py`
  - `src/warhammer40k_ai/engine/replay.py`
  - `src/warhammer40k_ai/engine/time_manager.py`
  - `src/warhammer40k_ai/engine/tier1_plan.py`
  - `src/warhammer40k_ai/engine/tier2_orchestrator.py`
  - `src/warhammer40k_ai/engine/movement_intent.py`
  - `src/warhammer40k_ai/engine/movement_solver.py`
  - `src/warhammer40k_ai/engine/path_witness.py`
- If these behaviors change, update:
  - `docs/DECISION_RECORD_TELEMETRY.md`
  - `docs/DECISION_RECORD_REPLAY.md`
  - `docs/STATE_BLOB_SCHEMA.md`
  - `docs/TIER1_PLAN_SCHEMA.md`
  - `docs/TIER2_ORCHESTRATION.md`
  - `docs/TIME_MANAGER_POLICY.md`
  - `docs/MOVEMENT_INTENT.md`
  - `docs/PATH_WITNESS_CONTRACT.md`
  - `docs/TIGHT_CLEARANCE_POLICY.md`

## 8) Multiplayer/Network and AI-Readiness Architecture
### Network/multiplayer (future WebSockets)
- State/events must be serializable and synchronizable.
- Avoid hidden/non-serializable state (file handles, unstructured globals, lambdas/closures in state).
- Prefer explicit schemas for snapshots and incremental events/commands, with deterministic entity ids.
- Determinism: RNG injectable/seedable; transitions reproducible from event log.
- When adding state/events, design for encode/decode + validation over network boundaries.

### UI dialog mapping (mandatory)
- Every new UI dialog must map to a deterministic, serializable decision/action.
- Update `docs/NETWORK_SAVELOAD_DESIGN.md` UI dialog-to-decision mapping entries for new dialogs.

### HRL/engine-first constraints (future AI)
- All human choices must map to explicit decision points with finite/clearly bounded action spaces.
- All keyboard/mouse interactions must map to explicit actions with payloads (coords, target IDs, option IDs).
- Engine must run without interactive UI; UI is a client of the same decision/action interface as AI.
- Engine emits required decisions; controller (human/AI) returns chosen actions; engine validates/applies deterministically.
- Any feature introducing player choice must include decision/action definition, validation rules, and tests covering one valid and one invalid path.

## 9) AI Reintroduction Non-Negotiables
- Every player decision must emit DecisionRecord compliant with `docs/DECISION_RECORD_SCHEMA.json`.
- DecisionRecord must include: `global_seed`, `decision_seed`, `candidates`, `mask`, `chosen_action_id` (when valid), `wall_clock_ms`, `outcome`.
- HumanActionCandidate injection is required when UI permits freeform actions not present in solver top-K (movement first).
- Rejected human actions must log `valid=false` with `invalid_attempt` and `rejection_reason`.

### Candidate determinism
- Candidate lists must be deterministic.
- `CandidateAction.action_id` must be replay-stable and derived from canonical params (or canonical hash).
- Any randomized candidate generation must use injected RNG and be reproducible from `decision_seed`.

### Time-budget enforcement
- Candidate-generating solvers must accept and obey `time_budget_ms`.
- On timeout: return best-so-far candidates and record fallback mode metadata.
- Record `time_budget_ms` and `wall_clock_ms` in each DecisionRecord.

### Movement PathWitness
- `MOVE_UNIT`, `CHARGE_MOVE`, and `FALL_BACK` decisions must produce full PathWitness artifact (or reference).
- Validate legality continuously along path; endpoint-only checks are invalid.

### Stratagem/enhancement tool descriptors
- New stratagem/enhancement support must include/update structured tool descriptors
  (timing, target constraints, cost, effect params, duration).
- Do not hardcode bespoke effects outside the tool-descriptor layer unless explicitly approved.

### AI/ML dependency policy
- Do not add PyTorch/TorchRL/PyG/Ray/W&B to core dependencies before dedicated ML-boundary milestone.
- ML deps must be optional extras and isolated (e.g. `warhammer40k_ai/ml/`).
- Engine must run headless and support replay without ML stack installed.

### AI compatibility checklist
- New choices go through Decision API and preserve network parity.
- New decision types emit schema-valid DecisionRecords.
- Candidate ordering/action IDs are deterministic.
- Time budgets enforced for new candidate generation.
- Movement changes preserve PathWitness invariants.
- Docs updated in `docs/` and in network save/load mapping when UI changes.

## 10) Ambiguity, Distance, and Escalation
- If uncertain about rules accuracy, timing, intent, data interpretation, or latest-version ambiguity (FAQ/errata/dataslate/MFM), ask developer before coding.
- Do not guess nuanced rules; provide concrete questions plus recommended interpretation and wait for direction.
- Distance/range is 3D unless a rule explicitly states horizontal/vertical measurement.
- Stop and ask developer for:
  - out-of-scope content requests,
  - large architecture-direction refactors,
  - cases requiring non-latest rules due to source gaps.
- Escalation message must include: what was found, proposed path, risks/tradeoffs, and a small-step implementation plan.
